# RPKI Warehouse API

The REST API behind [RPKI Warehouse](https://rpki.netsecurelab.org), a longitudinal record of the
RPKI objects published under the five RIRs, from 2012 to today. It reads the Parquet warehouses
that rpki-parser builds. Collection with rpki-client runs every 20 minutes; history before April
2026 comes from the RIPE NCC RPKI archive. The API is built on FastAPI and DuckDB.

The public API is at `https://rpki.netsecurelab.org/api/<endpoint>`. It needs no key, and each
client may send 60 requests per minute. This component also holds two batch pipelines: the daily
country analytics build (`pipelines/country/`) and the weekly RPKI operations scorecard
(`pipelines/scorecard/`). [ARCHITECTURE.md](../ARCHITECTURE.md) in the
[rpki-health](https://github.com/taejoong/rpki-health) repository shows how the parser, this API
and the web UI fit together.

## Quick Start

You need the warehouse directories that the parser writes (`warehouse-{rir}/`, each with
`snapshots/`, `indexes/` and `tables/`) and a machine with a lot of memory (see
[Configuration](#configuration)). By default the API reads them from the parser next to this
directory: `../rpki-parser/warehouse-{rir}/` for separate checkouts, or `../parser/warehouse-{rir}/`
in the rpki-health repository. It writes its request log to `data/analytics.db`. `WAREHOUSE_BASE`
and `ANALYTICS_DB` in `app/config.py` change that. RIRs without a warehouse are skipped. Then:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

At startup the server builds five in-memory tables from the warehouses (about 6 minutes for the
production data). It then serves queries against both the in-memory tables (fast lookups) and the
on-disk Parquet files (historical queries).

**OpenAPI docs**: http://localhost:8000/docs

## Architecture

```
FastAPI (app/main.py), one process
  |
  +-- DuckDB in-memory tables, built at startup and on each reload:
  |     live_roas, roa_history, current_invalid, ca_certs, ca_resource_map
  |
  +-- DuckDB -> Parquet on disk, read per request
  |     WAREHOUSE_BASE/warehouse-{rir}/tables/
  |
  +-- Country analytics build (written by pipelines/country), read per request
  |     COUNTRY_RPKI_DIR/current/
  |
  +-- HTTPS: the lab's BGP warehouse API (coverage) and ASINT API (organizations)
  |
  +-- SQLite: request log (ANALYTICS_DB)
```

### Data Source

Parquet warehouses generated by the `rpki-parser` ETL pipeline, one per RIR:

- **5 main RIRs**: AFRINIC, APNIC, ARIN, LACNIC, RIPE NCC
- **Snapshots**: one per day from the RIPE NCC RPKI archive since 2012 (ARIN since 2012-09-24),
  then one per rpki-client run (every 20 minutes, up to 72 per day) since 2026-04-08. APNIC's
  2012-10-27 to 2018-04-04 lives in separate sub-TAL warehouses, which only the country pipeline
  reads.
- **Tables the API reads** (`tables/table=<name>/`): `roa_objects`, `roa_prefixes`, `certs`,
  `crls`, `manifests`, `aspa_objects`, `aspa_providers`, `object_signatures`, `object_validity`
  (the objects rpki-client rejected, per cycle) and `object_presence_stats` (first and last seen
  of each object)

### Tech Stack

- **Python 3.10+** with FastAPI (tested with Python 3.14)
- **DuckDB** for Parquet queries (no ORM, raw SQL)
- **Pydantic v2** response models
- **SQLite** for the request log
- Auto-generated OpenAPI/Swagger docs

## Example Queries

```bash
# Live VRPs for exactly 1.0.0.0/24 (a covering ROA, e.g. a /22 with maxLength 24, is not listed)
curl "http://localhost:8000/roa/lookup?prefix=1.0.0.0/24"

# All ROAs for Cloudflare (AS13335)
curl "http://localhost:8000/roa/by-asn?asn=13335"

# Full history of 1.0.0.0/24 since 2018
curl "http://localhost:8000/roa/history?prefix=1.0.0.0/24"

# ARIN ROA churn, monthly, 2025
curl "http://localhost:8000/analytics/churn?rir=arin&granularity=month&start=2025-01&end=2025-12"

# ROAs with maxLength excess >= 8 bits
curl "http://localhost:8000/analytics/maxlength-issues?rir=ripencc&min_excess=8"

# ASPA deployment stats
curl "http://localhost:8000/aspa/stats"

# Recent Cloudflare ROA changes in APNIC
curl "http://localhost:8000/alerts/recent?rir=apnic&asn=13335&days=30"

# Compare ROA growth across all RIRs
curl "http://localhost:8000/analytics/rir-comparison?metric=roa_count&start=2025-01&end=2025-12"

# ROA deployment per RIR over time, then South Korea and its top origin ASes (IPv4)
curl "http://localhost:8000/analytics/country/rir-trend?af=4"
curl "http://localhost:8000/analytics/country/trend?cc=KR&af=4"
curl "http://localhost:8000/analytics/country/ases?cc=KR&af=4&sort=routes&order=desc&limit=20"
```

These examples query a local server. For the public API, replace `http://localhost:8000` with
`https://rpki.netsecurelab.org/api`.

## Data and Methods

### Lifecycle timestamps

**`first_seen` / `last_seen` everywhere in the API come from `object_presence_stats`** (via
`_presence_src()` in `app/db.py`), and `live_cutoff()` = `MAX(last_ts) − 1 day`. So if the daily
presence build stops, ingestion keeps working but every object's `last_seen` freezes and "live"
queries drift. Quick check, from the parser directory (`rpki-parser`, or `parser/` in the rpki-health
repository):

```bash
.venv/bin/python -c "import duckdb; print(duckdb.sql(\"select max(last_ts) from read_parquet('warehouse-arin/tables/table=object_presence_stats/*.parquet')\").fetchone())"
```

### Coverage method (`/roa/coverage`, `/roa/org-coverage`)

- **Announced:** a prefix counts as announced by AS X if any of `route-views2`, `route-views6`
  or `rrc00` saw X originate it in the last 7 daily RIBs (`window_days`, default 7). The window
  ends at the newest day all three collectors have in the BGP warehouse. A collector more than
  3 days behind the others is left out and listed in `method.skipped_collectors`. Prefixes
  longer than /24 (IPv4) or /48 (IPv6) are not counted (`excluded_more_specifics`). They are
  not globally routable and come from single peers' internal routes. For example, about 900
  /26–/27s of AS3356 are seen only via AS3549.
- **Validation:** each announced (prefix, X) is origin-validated against the live VRPs
  (RFC 6811). It is *valid* when a VRP for X covers it within maxLength; *invalid* when it is
  covered, but only by VRPs for other ASes or with a shorter maxLength; *not_found* when no VRP
  covers it. `coverage_pct` is the valid share. Every response echoes this in `method`.

Before 2026-10-25 the page counted every prefix route-views2 had *ever* seen since 2020 (for
example AS13335: 4,539 announced instead of ~5,800 current). It also used IPv6 data that stops in
2021, and it required an exact prefix string match. Under that rule a /24 announced under a /22
ROA with maxLength 24 counted as unsigned. Coverage numbers from before and after that date are
not comparable.

### Country analytics (`/analytics/country/*`)

The Analysis → Countries page serves a precomputed daily build; no request does BGP or RPKI work.

- **Data dir:** `COUNTRY_RPKI_DIR` in `app/config.py` (default `/ssd-data/country-rpki`) with
  `inputs/`, `pairs/`, `daily/`, `builds/<YYYYMMDDTHHMMSSZ>/` and `current -> builds/<stamp>`.
- **Producer contract:** `pipelines/country` (`crc.assemble`) writes `manifest.json`,
  `series.parquet` (every grid date × `level` all/registry/cc × `key` × `af`), `countries.parquet`
  (each country at `as_of`, plus `prev_*` at `prev_date`, one year earlier), `ases.parquet` (origin
  ASes per country at `as_of`) and `as_series.parquet` (per-AS monthly history) into
  `builds/<stamp>.tmp`, renames it, and swaps `current` with
  `ln -s builds/<stamp> current.new && mv -T current.new current`. It keeps the newest 3 builds,
  never uses `key=value` directory names, and writes NULL instead of NaN/Inf. Units: IPv4
  addresses, IPv6 /48s. Dates are UTC days on a grid of Wednesdays 2012-01-04 → 2025-12-31,
  then every day; the BGP-based lenses start 2020-01-01.
- **Serving:** the router reads `current` lazily with `read_parquet(..., hive_partitioning = false)`
  on the shared connection and is not part of `init_db()`/`hot_reload()`. A new build needs no
  restart or reload: the first request after the swap serves it (the manifest is re-read only when
  `realpath(current)` changes). `meta`, `countries` and `rir-trend` are response-cached per build
  as rendered JSON; `trend`, `ases` and `as-trend` are filtered reads per request.
- **Before the first build** every endpoint returns 503 `Country analytics not built yet` (503
  `Country analytics build unreadable` if its manifest or a Parquet file is missing or unreadable).
- **Refresh:** daily by `pipelines/country/run_daily.sh`, which holds `flock ROOT/.lock`.
  Schedule, backfill and recompute commands: `pipelines/country/README.md`.

## Deployment

The public site runs this API as one uvicorn process. That process holds the one in-memory
DuckDB, so one `/admin/reload` refreshes everything. It listens only on the loopback interface of
the host that holds the rpki-parser warehouses. A Cloudflare Tunnel publishes it, and the site's
Cloudflare Pages Function (rpki-frontend, `functions/api/`) forwards
`https://rpki.netsecurelab.org/api/*` to it.

Cron jobs on the same host run the rpki-parser collection cycle (every 20 minutes), its daily
presence rebuild, `pipelines/country/run_daily.sh` (daily), `pipelines/scorecard/run_weekly.sh`
(Mondays) and `POST /admin/reload?wait=true` (every 30 minutes). The host configuration (crontab, systemd units, tunnel, log rotation and
backups) is kept in a private operations repository. [ARCHITECTURE.md](../ARCHITECTURE.md) in the
[rpki-health](https://github.com/taejoong/rpki-health) repository describes the whole system: its
components, schedule, locks and data flow.

### Reload

`init_db()` (startup, ~6 min) and `hot_reload()` both go through `_build_tables()`, so they
materialize the same tables: `current_invalid`, `live_roas`, `roa_history`, `ca_certs`,
`ca_resource_map`. A reload builds them as `<name>_new` while the old ones keep serving, then
swaps all five in one transaction. Until 2026-10-25 the reload skipped the two CA tables, so CA
Explorer (`/ca/*`) showed the state of the last process start. Both
`init_db()` and `hot_reload()` hold `/tmp/rpki_presence.lock` shared, so they wait for the 01:00
presence rebuild, which rewrites `object_presence_stats` in place, instead of reading
half-written parts.

If the presence rebuild still holds the lock after 30 minutes, a reload gives up and the next
cron run retries; startup goes ahead without the lock.

`POST /admin/reload` requires `X-Reload-Token`, the token the reload cron job holds, and the rate
limiter skips that path. Without the token file the endpoint
returns 503. The response is 409 while a reload is already running and 202 when it starts in the
background. With `?wait=true` it is 200 or 500 depending on the result. The rebuild always runs
on a daemon thread, so running uvicorn with `--timeout-graceful-shutdown 10` lets a restart
mid-reload exit within seconds.

### Visitor IP and the proxy token

The rate limiter (60 requests/min per key) and the visitor log key each request on `client_ip()`
(`app/client_ip.py`); the limiter keys IPv6 clients on their /64. The Pages Function (`rpki.netsecurelab.org/api/*`)
passes the visitor's address as `X-Visitor-IP`, which counts only with an `X-Proxy-Token` equal
to `~/.config/rpki-proxy.token`; the Pages secret `PROXY_TOKEN` holds the same value. Anything
else is keyed on `CF-Connecting-IP`. If the two values differ, or the Production deployment of
the Function does not send the token, all visitors of the site share the Function's one key and
get 429s. The journal says `Proxy token loaded` when the file is read, and `No proxy token` or
`X-Visitor-IP ignored` (at most every 5 min) when the header is not trusted. The file is re-read
when it changes, so no restart is needed, but only one value is accepted. To rotate:

1. `( umask 077; openssl rand -hex 32 > ~/.config/rpki-proxy.token.new )`
2. `tr -d '\n' < ~/.config/rpki-proxy.token.new | npx wrangler pages secret put PROXY_TOKEN --project-name <project>`
3. In a `main` checkout of the frontend, `npm run build && npx wrangler pages deploy dist
   --project-name <project> --branch main` (a secret only reaches new deployments), and as
   soon as it finishes, `mv ~/.config/rpki-proxy.token.new ~/.config/rpki-proxy.token`.

Pages secrets cannot be read back, so a lost token file means a new token, set the same way.

## Configuration

Settings are constants in `app/config.py`:

- `WAREHOUSE_BASE`: the directory that holds `warehouse-{rir}/` (default: the parser next to this
  directory, `../rpki-parser` or else `../parser`)
- `ANALYTICS_DB`: the SQLite request log the API writes (default `data/analytics.db` in this
  checkout, created at startup)
- `RIRS`: List of RIR names to load
- `COUNTRY_RPKI_DIR`: Country analytics data dir (default: `/ssd-data/country-rpki`; the API serves `current/`)
- `PRESENCE_LOCK_FILE`: the lock that rpki-parser's daily presence rebuild holds (default
  `/tmp/rpki_presence.lock`)
- `BGP_WAREHOUSE_URL`, `BGP_WAREHOUSE_KEY_FILE` (API key, default `~/.config/bgp-warehouse.key`):
  the lab's BGP warehouse API, for `/roa/coverage` and `/roa/org-coverage`.
  `BGP_COVERAGE_COLLECTORS` and `BGP_COVERAGE_WINDOW_DAYS` set what counts as announced.
- `ASINT_API_URL`: the ASINT API, for the organization endpoints
- Token files, one line each: `ADMIN_TOKEN_FILE` (`/admin/stats`), `STATS_TOKEN_FILE` (`/stats`)
  and `RELOAD_TOKEN_FILE` (`POST /admin/reload`), all under `~/.config/` by default. Each is
  read on every request and compared in constant time. Without the file, its endpoint returns
  503. For `PROXY_TOKEN_FILE`, see [Visitor IP and the proxy token](#visitor-ip-and-the-proxy-token).
- CORS origins: `app/main.py`
- DuckDB settings in `app/db.py` (`init_db()`): `threads = 16`, `memory_limit = '64GB'`. A reload
  is a 30+ GB rebuild that runs while the old tables keep serving. Lower the settings on a
  smaller machine.

The request log (`ANALYTICS_DB`) records the time, client IP address, country, user agent, path
and query of each GET request, except `/health`, `/stats`, `/admin/*` and the API docs. Values of
query parameters named `token`, `key`, `password` or `secret` are stored as `redacted`.
`/admin/stats` and `/stats` read it.
